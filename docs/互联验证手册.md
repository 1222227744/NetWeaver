# NetWeaver 互联验证手册

本手册的目标不是“介绍原理”，而是让联调人员能够按顺序执行命令，完整验证 NetWeaver 当前已经实现的功能，并在失败时知道第一时间该看哪里。

- 前端联调说明：[README.md](/D:/Documents/WorkSpace/30-Playground/frontend/planA/NetWeaver/frontend/README.md)
- 当前接口契约：[NetWeaver-API-v1.8.md](/D:/Documents/WorkSpace/30-Playground/frontend/planA/NetWeaver/docs/NetWeaver-API-v1.8.md)

## 一、先说结论标准

本项目的“互联成功”不能只看页面上有节点，也不能只看有边，必须分三层判断：

1. 控制面成功。
原因：这表示节点至少能注册、发心跳、同步对端信息。
通过标准：Dashboard 能看到节点在线，节点日志里能持续出现注册和心跳相关日志。

2. 链路层成功。
原因：这表示 Controller 已经收到节点上报的真实建链结果，而不是前端写死的数据。
通过标准：`GET /api/v1/dashboard/edges` 返回真实边，边的 `type` 是 `p2p` 或 `relay`。

3. 数据面成功。
原因：这才是真正证明“虚拟网络已经互通”的标准。
通过标准：开启 TUN 后，节点之间能通过各自 `virtual_ip` 相互 `ping` 通。

所以请记住：

- 只看到节点在线，不代表互联成功。
- 只看到关系图有边，不代表数据真的通了。
- 只有 `virtual_ip` 能互 ping，才能算最终互联成功。

## 二、这份手册适用的联调场景

本手册适合下面两类场景：

1. 课程联调。
场景：1 台服务器跑 Controller，2 到 3 台电脑跑 Node，前端用浏览器访问 Dashboard。

2. 局域网 / 校园网现场演示。
场景：老师或评审在现场看你们操作，要求你们展示“节点上线、形成链路、节点下线、重新上线、查看延迟、验证虚拟 IP 互通”。

## 三、联调角色分工

为了避免现场混乱，建议把联调参与者按角色分开：

1. 服务器角色。
职责：启动 Controller 和 UDP Relay，保存后端日志，提供 Dashboard HTTP 地址。

2. 节点角色。
职责：分别在各自机器上启动 Node，观察本机日志，执行 TUN 配置和 `ping`。

3. 前端角色。
职责：打开 Dashboard，登录，观察节点、边、延迟曲线和离线恢复。

## 四、联调前准备

### 1. 机器准备

建议至少准备这些设备：

1. 1 台服务器。
用途：运行 Controller 和 UDP Relay。

2. 2 台客户端电脑。
用途：运行两个真实 Node，完成最小互联闭环。

3. 可选第 3 台客户端电脑。
用途：把演示从“两点互联”扩展成“三点网络”。

### 2. 软件准备

服务器和各节点机器都需要：

- 拉取当前仓库代码
- 能运行 Go
- 能执行 `go run ./cmd/controller` 或 `go run ./cmd/node run`

前端机器需要：

- 能运行 `npm run dev`
- 浏览器可以访问 Controller 的 HTTP 地址

### 3. 网络准备

服务器至少需要放行这些端口：

- `8080/tcp`
- `9000/udp`

原因：

- `8080/tcp` 是 Controller HTTP 接口和 Dashboard API 入口。
- `9000/udp` 是 Relay 的默认端口。

如果服务器防火墙没放行：

- 前端会登录失败或请求超时。
- Node 能否注册和心跳也会受到影响。
- 即使节点上线，Relay 回退也可能失败。

### 4. 变量约定

请在联调前先统一这些值：

```text
<SERVER_IP>            服务器对所有节点都可达的真实 IP
<CONTROLLER_URL>       http://<SERVER_IP>:8080
<RELAY_ADDR>           <SERVER_IP>
<RELAY_PORT>           9000
<DASHBOARD_USERNAME>   你们实际使用的控制台用户名
<DASHBOARD_PASSWORD>   你们实际使用的控制台密码
<NODE_PSK>             你们实际使用的节点 PSK
```

如果还是使用开发默认值，也可以这样理解：

```text
<DASHBOARD_USERNAME> = admin
<DASHBOARD_PASSWORD> = change-me
<NODE_PSK> = netweaver-dev-psk
```

但真正演示或落地前，建议你们换掉这些默认值。

## 五、联调总流程概览

完整联调建议按这个顺序做：

1. 先启动服务器上的 Controller。
原因：没有 Controller，前端和节点都无从连接。

2. 再启动前端 Dashboard。
原因：这样节点一上线，你们就能立刻从页面观察结果。

3. 然后启动 2 到 3 个 Node，先用 `-tun=false` 做控制面和链路层验证。
原因：先排除 TUN 权限影响，确保“注册、心跳、建边、关系图、metrics”先闭环。

4. 控制面和链路层通过后，再切到 TUN 模式验证数据面。
原因：如果一开始就带 TUN，现场一旦失败，你们很难快速判断是控制面问题、链路问题还是 TUN 权限问题。

5. 最后做功能性演示。
原因：包括离线恢复、关系图更新、边类型变化、延迟图显示等，这些都更适合在系统已经稳定后展示。

## 六、服务器端完整步骤

### 步骤 1：进入后端目录

```bash
cd backend
```

原因：

- 当前 Go 模块根目录就是 `backend`
- 后面的 `go run ./cmd/...` 和 `go test ./...` 都以这里为基准

### 步骤 2：设置关键环境变量

```bash
export NETWEAVER_DASHBOARD_USERNAME='<DASHBOARD_USERNAME>'
export NETWEAVER_DASHBOARD_PASSWORD='<DASHBOARD_PASSWORD>'
export NETWEAVER_JWT_SECRET='replace-with-your-own-secret'
export NETWEAVER_NODE_PSK='<NODE_PSK>'
export NETWEAVER_RELAY_ADDR='<RELAY_ADDR>'
export NETWEAVER_RELAY_PORT=9000
```

如果你们还没有自己的 STUN 规划，可以暂时不设置 `NETWEAVER_STUN_SERVERS`。

原因：

- `NETWEAVER_RELAY_ADDR` 必须设置成服务器真实 IP，否则节点可能拿到 `127.0.0.1` 这种错误地址。
- `NETWEAVER_NODE_PSK` 必须和所有 Node 保持一致，否则注册和心跳会失败。
- Dashboard 用户名密码需要和前端登录保持一致。

### 步骤 3：启动 Controller

```bash
go run ./cmd/controller
```

原因：

- 当前 Controller 会同时提供 HTTP API 和 UDP Relay。
- 你们不需要再额外启动一个单独的 Relay 进程。

预期现象：

- 终端里应看到 HTTP 服务启动日志。
- 终端里应看到类似 `udp relay listening on ...` 的日志。

### 步骤 4：验证 Controller 是否真的可用

```bash
curl http://127.0.0.1:8080/ping
```

预期输出：

```json
{"msg":"pong"}
```

原因：

- 这个检查最简单，能先证明 HTTP 服务已经起来。

### 步骤 5：验证登录接口可用

```bash
curl -X POST http://127.0.0.1:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"<DASHBOARD_USERNAME>","password":"<DASHBOARD_PASSWORD>"}'
```

预期结果：

- 返回 `code: 200`
- 返回 `data.token`

原因：

- Dashboard 登录失败时，首先要确认是不是前端问题。
- 这一步直接用 `curl` 能先证明后端登录接口本身正常。

## 七、前端端完整步骤

### 步骤 1：配置前端代理地址

在 `frontend/.env.development.local` 中填写：

```env
VITE_API_BASE_URL=
VITE_PROXY_TARGET=http://<SERVER_IP>:8080
```

原因：

- 当前项目开发联调最推荐走 Vite 代理。
- 这样浏览器继续请求 `/api/...`，由 Vite 转发到真实后端。
- 相比浏览器直接跨域访问，这种方式更稳定，也更容易排查。

### 步骤 2：启动前端开发服务

```powershell
cd frontend
npm run dev
```

原因：

- 前端当前不是纯静态页面，而是要实时请求后端接口。

### 步骤 3：用浏览器打开控制台

打开 Vite 提示的地址，一般类似：

```text
http://127.0.0.1:5173
```

### 步骤 4：登录 Dashboard

使用和服务器环境变量一致的账号密码登录。

预期现象：

- 登录后页面切换到控制台主体
- 顶部有“总节点数、在线节点、链路数、运行时长”四张统计卡片
- 页面不会出现 401 或接口错误提示

原因：

- 这一步是在验证 JWT 登录和 `dashboard/*` 请求闭环是否成立。

## 八、节点端完整步骤

这一部分先做“不带 TUN”的基础联调，再做“带 TUN”的数据面联调。

### A. 先做不带 TUN 的基础联调

#### 步骤 1：确认本机要上报的局域网 IP

在 Linux / WSL 中可以先看：

```bash
hostname -I
```

或者：

```bash
ip route get 1.1.1.1
```

原因：

- `-local-ip` 应尽量填写真实参与联调的本机地址。
- 如果写错成本地回环地址、Docker 网卡地址或无效网卡地址，页面上的节点信息会不准确。

#### 步骤 2：启动第 1 个节点

```bash
cd backend
export NETWEAVER_NODE_PSK='<NODE_PSK>'

go run ./cmd/node run \
  -controller http://<SERVER_IP>:8080 \
  -machine-id nw-node-a \
  -hostname node-a \
  -local-ip <NODE_A_LOCAL_IP> \
  -data-addr 0.0.0.0:9101 \
  -tun=false
```

原因：

- `-machine-id` 用来稳定标识同一台节点，后面验证身份复用时会用到。
- `-data-addr` 是该节点用于 STUN、打洞和数据面的 UDP 地址。
- `-tun=false` 是为了先排除 TUN 权限问题。

#### 步骤 3：启动第 2 个节点

```bash
cd backend
export NETWEAVER_NODE_PSK='<NODE_PSK>'

go run ./cmd/node run \
  -controller http://<SERVER_IP>:8080 \
  -machine-id nw-node-b \
  -hostname node-b \
  -local-ip <NODE_B_LOCAL_IP> \
  -data-addr 0.0.0.0:9102 \
  -tun=false
```

如果你们要做三节点，再增加一个：

```bash
cd backend
export NETWEAVER_NODE_PSK='<NODE_PSK>'

go run ./cmd/node run \
  -controller http://<SERVER_IP>:8080 \
  -machine-id nw-node-c \
  -hostname node-c \
  -local-ip <NODE_C_LOCAL_IP> \
  -data-addr 0.0.0.0:9103 \
  -tun=false
```

补充说明：

- 如果节点跑在不同机器上，`9101`、`9102`、`9103` 这些端口可以重复使用。
- 如果多个节点跑在同一台机器上，`data-addr` 端口必须不同。

#### 步骤 4：观察节点日志

重点关注这些内容：

- 节点注册成功日志
- 心跳成功日志
- peers 同步日志
- P2P 打洞失败后回退到 Relay 的日志

为什么要看日志：

- 日志是定位问题最快的入口。
- 页面只会告诉你“有没有节点、有没有边”，但不会完整告诉你打洞为什么失败。

#### 步骤 5：观察 Dashboard 页面

通过标准：

1. 统计卡片中的总节点数、在线节点数与实际启动数一致。
2. 节点表里能看到 `node-a`、`node-b`，以及可选的 `node-c`。
3. 每个节点都有 `node_id`、`virtual_ip`、`public_ip`、`nat_type`、`status`。
4. 节点表按当前实现会把在线节点排在前面。

原因：

- 这一步验证的是控制面闭环：注册、心跳、状态刷新、前端渲染。

### B. 再做 API 层验证

#### 步骤 1：获取 Dashboard JWT

如果本机有 `jq`，可以用：

```bash
TOKEN=$(curl -s -X POST http://<SERVER_IP>:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"<DASHBOARD_USERNAME>","password":"<DASHBOARD_PASSWORD>"}' | jq -r '.data.token')

echo "$TOKEN"
```

如果没有 `jq`，也可以先直接看完整返回：

```bash
curl -s -X POST http://<SERVER_IP>:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"<DASHBOARD_USERNAME>","password":"<DASHBOARD_PASSWORD>"}'
```

原因：

- `dashboard/*` 接口都需要 JWT。
- 后面验证 `stats`、`nodes`、`edges`、`metrics` 都要用这个 token。

#### 步骤 2：验证 stats

```bash
curl -s http://<SERVER_IP>:8080/api/v1/dashboard/stats \
  -H "Authorization: Bearer $TOKEN"
```

通过标准：

- `code` 为 `200`
- `online_nodes` 与当前在线节点数一致
- `total_edges` 会随着建链结果变化

原因：

- 这一步验证前端顶部统计卡片的数据来源是否真实。

#### 步骤 3：验证 nodes

```bash
curl -s http://<SERVER_IP>:8080/api/v1/dashboard/nodes \
  -H "Authorization: Bearer $TOKEN"
```

通过标准：

- `code` 为 `200`
- `data.nodes` 中至少能看到 2 个在线节点
- 字段中应包含 `node_id`、`hostname`、`virtual_ip`、`public_ip`、`nat_type`、`status`

原因：

- 这一步验证前端节点表和关系图中的节点是否来自真实接口。

#### 步骤 4：验证 edges

```bash
curl -s http://<SERVER_IP>:8080/api/v1/dashboard/edges \
  -H "Authorization: Bearer $TOKEN"
```

通过标准：

- `code` 为 `200`
- `data.edges` 里能看到至少 1 条边
- 边的 `type` 只能是 `p2p` 或 `relay`

为什么这一步重要：

- 它直接验证关系图的连线是不是来源于真实后端状态。
- 如果一直没有边，前端关系图当然也不会显示连线。

#### 步骤 5：验证 metrics

先从页面或 `nodes` 接口里记下两个节点的 `node_id`。

然后执行：

```bash
curl -s "http://<SERVER_IP>:8080/api/v1/dashboard/nodes/<SOURCE_NODE_ID>/metrics?target_id=<TARGET_NODE_ID>&time_range=1h" \
  -H "Authorization: Bearer $TOKEN"
```

通过标准分两种：

1. 返回 `code: 200` 且 `metrics` 为非空数组。
说明：链路已经有真实延迟采样点，前端可以画曲线。

2. 返回 `code: 200` 且 `metrics: []`。
说明：两个节点存在，但当前时间范围内还没有采样点，这不是接口失败。

原因：

- 当前前端的悬浮延迟图就是消费这个接口。
- 这个接口为空数组时，前端会显示“暂无链路数据”，这是正常空态。

## 九、TUN 数据面完整验证步骤

这一部分是最关键的最终验收。

### 步骤 1：先停掉当前 `-tun=false` 运行的节点

在每台节点终端里按：

```text
Ctrl + C
```

原因：

- 你们现在要切换到真正的 TUN 数据面验证，不能继续沿用无 TUN 模式。

### 步骤 2：每台节点机器创建一次持久化 TUN 设备

```bash
cd backend
sudo $(which go) run ./cmd/node tun -bootstrap -ifname nw0
```

原因：

- `-bootstrap` 会创建持久化 TUN，并尽量把权限处理成后续普通用户也能运行的状态。
- `nw0` 只是一个示例名字，你们也可以统一用 `tuno`，但联调时统一命名更省事。

执行后检查：

```bash
ip link show nw0
```

通过标准：

- 能看到 `nw0` 设备

### 步骤 3：重新以 TUN 模式启动节点

node-a：

```bash
cd backend
export NETWEAVER_NODE_PSK='<NODE_PSK>'

go run ./cmd/node run \
  -controller http://<SERVER_IP>:8080 \
  -machine-id nw-node-a \
  -hostname node-a \
  -local-ip <NODE_A_LOCAL_IP> \
  -data-addr 0.0.0.0:9101 \
  -tun-name nw0 \
  -tun-auto-config \
  -tun-auto-cleanup
```

node-b：

```bash
cd backend
export NETWEAVER_NODE_PSK='<NODE_PSK>'

go run ./cmd/node run \
  -controller http://<SERVER_IP>:8080 \
  -machine-id nw-node-b \
  -hostname node-b \
  -local-ip <NODE_B_LOCAL_IP> \
  -data-addr 0.0.0.0:9102 \
  -tun-name nw0 \
  -tun-auto-config \
  -tun-auto-cleanup
```

原因：

- 这一次没有写 `-tun=false`，所以节点会尝试启动真实数据面。

### 步骤 4：从页面或日志获取每个节点的 `virtual_ip`

推荐从 Dashboard 节点列表中抄下来。

示例：

```text
node-a -> 10.0.0.2
node-b -> 10.0.0.3
node-c -> 10.0.0.4
```

注意：

- 请以当前页面或日志里的真实值为准，不要死记旧值。
- `machine-id` 稳定时，节点重新上线通常会复用原来的 `node_id` 和 `virtual_ip`，但仍建议你们现场确认一次。

### 步骤 5：推荐直接用自动参数完成 `nw0` 配置

如果你们已经使用下面这种启动方式：

```bash
go run ./cmd/node run \
  -controller http://<SERVER_IP>:8080 \
  -machine-id nw-node-a \
  -hostname node-a \
  -local-ip <NODE_A_LOCAL_IP> \
  -data-addr 0.0.0.0:9101 \
  -tun-name nw0 \
  -tun-auto-config \
  -tun-auto-cleanup
```

那么节点注册拿到 `virtual_ip` 后，会自动执行：

- 给 `nw0` 绑定自己的 `virtual_ip`
- 把 `nw0` 拉起
- 进程退出时自动删除这次自动添加的地址并把网卡 down 掉

也就是说，联调时推荐优先使用自动参数，不再手工敲 `ip addr replace ...` 和 `ip link set ... up`。

### 步骤 6：如果当前机器不能用自动参数，再手工配置 `virtual_ip`

假设 node-a 的 `virtual_ip` 是 `10.0.0.2`：

```bash
sudo ip addr replace 10.0.0.2/16 dev nw0
sudo ip link set nw0 up
ip addr show nw0
```

假设 node-b 的 `virtual_ip` 是 `10.0.0.3`：

```bash
sudo ip addr replace 10.0.0.3/16 dev nw0
sudo ip link set nw0 up
ip addr show nw0
```

原因：

- Node 进程负责拿到虚拟 IP 和处理数据面包。
- 但当前系统里的 TUN 网卡地址仍需要你们手动配置。

### 步骤 7：互相 `ping` 对端虚拟 IP

node-a ping node-b：

```bash
ping -I nw0 -c 4 10.0.0.3
```

node-b ping node-a：

```bash
ping -I nw0 -c 4 10.0.0.2
```

如果有 node-c，也可以两两互测。

通过标准：

- 能看到 `64 bytes from ...`
- 丢包率不是 `100%`

原因：

- 这是最终证明“数据面已经互通”的步骤。
- 只要这一步成功，你们就可以非常明确地说：节点之间已经通过虚拟网络互联成功。

### 步骤 8：验证“真实组网效果”而不只是 `ping`

`ping` 通过只能证明最基础的 ICMP 可达。为了证明这套虚拟网络已经能承载真实业务，建议继续做下面 3 组验证。

#### 验证 1：确认去往对端 `virtual_ip` 的路由确实走 `nw0`

node-a 执行：

```bash
ip route get 10.0.0.3
```

node-b 执行：

```bash
ip route get 10.0.0.2
```

通过标准：

- 输出里应出现 `dev nw0`
- 输出里应出现 `src <本机_virtual_ip>`

原因：

- 这说明系统把发往对端虚拟地址的流量交给了 TUN 网卡，而不是误走物理网卡或默认路由。

#### 验证 2：同时观察虚拟网卡流量和底层 UDP 封装流量

node-a 新开两个终端：

```bash
sudo tcpdump -ni nw0 icmp
```

```bash
sudo tcpdump -ni any udp port 9101 or udp port 9102 or udp port 9103
```

然后再执行：

```bash
ping -I nw0 -c 4 10.0.0.3
```

通过标准：

- `nw0` 抓包窗口能看到 ICMP Echo Request / Reply
- `any` 抓包窗口能看到对应的 UDP 数据报
- 两边节点日志里没有持续报错

原因：

- 这说明“业务包进入 TUN”与“业务包被节点程序封装后经 UDP 发出”这两段链路都在工作。

#### 验证 3：直接跑一个真实应用流量

如果节点机器装了 Python 3，可以这样测试。

node-b 执行：

```bash
python3 -m http.server 18080 --bind 10.0.0.3
```

node-a 执行：

```bash
curl http://10.0.0.3:18080
```

如果没有 `curl`，也可以在浏览器里打开：

```text
http://10.0.0.3:18080
```

通过标准：

- `curl` 或浏览器能拿到目录页或文件内容
- node-b 终端能看到来自 `10.0.0.2` 的访问日志

原因：

- 这一步比 `ping` 更接近真实组网效果，因为它验证了 TCP 应用流量也能穿过这张虚拟网络。

如果你们要在答辩或演示中体现“落地价值”，建议至少保留以下证据：

- `ip route get <peer_virtual_ip>` 输出
- `tcpdump` 抓到的 `nw0` ICMP 与底层 UDP 封装
- `curl http://<peer_virtual_ip>:18080` 成功输出

## 十一、常见失败与第一检查点

### 现象 1：前端登录失败

先检查：

1. Controller 是否真的启动成功。
2. `POST /api/v1/auth/login` 是否能通过 `curl` 成功。
3. 前端 `.env.development.local` 里的 `VITE_PROXY_TARGET` 是否指向正确的 Controller 地址。

### 现象 2：页面能打开，但没有任何节点

先检查：

1. Node 是否真的已经启动。
2. Node 的 `NETWEAVER_NODE_PSK` 是否与 Controller 一致。
3. Node 的 `-controller` 地址是否写对。
4. 服务器 8080 端口是否可达。

### 现象 3：节点在线，但没有边

先检查：

1. 两个节点是不是都在线。
2. 节点日志里有没有 peer 同步信息。
3. 有没有 P2P 打洞失败和 Relay 回退日志。
4. `GET /api/v1/dashboard/edges` 是否真的为空。

### 现象 4：边有了，但延迟图为空

先检查：

1. `metrics` 接口是不是返回 `[]`。
2. 如果返回 `[]`，这表示当前没有采样点，不一定是错误。
3. 先确认心跳是否持续、链路是否稳定存在。

### 现象 5：节点在线，但 `virtual_ip` ping 不通

先检查：

1. 节点日志里有没有 `TUN data plane enabled`。
2. `ip link show nw0` 是否存在。
3. `ip addr show nw0` 是否已经正确配置了本机自己的 `virtual_ip`。
4. 页面上的边类型是不是已经形成。
5. 如果边是 `relay`，检查服务器 `9000/udp` 是否放行，以及 `NETWEAVER_RELAY_ADDR` 是否填写为真实服务器 IP。

### 现象 6：`virtual_ip` 能 ping 通，但真实应用访问不通

先检查：

1. 目标机器上的服务是否真的已经启动。
2. 服务是否绑定在正确的地址上，例如 `10.0.0.3` 或 `0.0.0.0`。
3. 目标端口是否被本机防火墙拦截。
4. `ip route get <peer_virtual_ip>` 是否明确显示走 `dev nw0`。
5. `tcpdump -ni nw0` 能不能看到对应的 TCP 或 HTTP 流量。

## 十三、当前自动化是不是还不够

答案是：还不够，而且目前明显偏“研发联调形态”，还不是“给用户直接使用的产品形态”。

当前自动化不足主要体现在这些地方：

1. 启动步骤过长。
现在服务器、前端、每个节点都需要分别手输命令，现场很容易漏参数。

2. 环境变量靠人工记忆。
像 `NETWEAVER_RELAY_ADDR`、`NETWEAVER_NODE_PSK`、`VITE_PROXY_TARGET` 这些值，一旦某一台机器填错，现场就会出现“部分功能正常、部分功能异常”的情况。

3. TUN 自动化还不完整。
现在已经支持 `node run -tun-auto-config -tun-auto-cleanup` 自动完成“给 TUN 绑定本机 `virtual_ip`、拉起网卡、退出时清理”这一段流程，但前提仍然是机器具备 TUN 权限，并且已经完成持久化网卡准备，或者运行环境允许进程直接创建 TUN。
这说明联调门槛已经明显下降，但距离普通用户零配置使用还有差距。

4. 缺少一键验证脚本。
当前没有统一脚本帮你自动检查 Controller、Node、Dashboard、TUN、API、边、metrics 是否全部正常。

5. 一键部署方案刚起步。
当前仓库已经补上 `scripts/deploy_server.sh` 和 `scripts/install_systemd.sh`，可以把“服务器拉仓库、构建后端、构建前端、生成环境文件、生成 systemd unit”这一段流程收敛到脚本里，但它仍然属于面向课程项目和服务器运维同学的部署脚本，不是普通用户安装器。

## 十四、如果后面真的要落地给用户，应该怎么办

如果你们只是课程项目，到现在这一步已经足够做联调和演示了。

但如果你问“以后真的要给用户用，怎么避免他们手敲这么多命令”，答案应该是逐步做下面几层自动化。

### 第一层：先做开发联调自动化

最先应该补的是脚本，而不是先做复杂界面。

建议至少补：

1. `scripts/deploy_server.sh`
作用：一键执行后端编译、前端构建、环境模板生成和 controller 启动脚本准备，适合 Linux 服务器首次部署。

2. `scripts/install_systemd.sh`
作用：把上一步生成的 `netweaver-controller.service` 安装到 systemd，适合服务器常驻运行。

3. `scripts/start-node.sh`
作用：传入 `machine-id`、`hostname`、`local-ip`、`data-addr` 后自动启动一个 Node。

4. `scripts/bootstrap-tun.sh`
作用：自动创建持久化 TUN，并在不能直接依赖 `-tun-auto-config` 的环境里提供兜底初始化能力。

5. `scripts/check-api.sh`
作用：自动请求 `ping`、`login`、`stats`、`nodes`、`edges`、`metrics`，输出是否通过。

为什么先做这层：

- 这是最省时间、收益最大的自动化。
- 你们自己下次联调也会轻松很多。

### 第二层：做单机打包启动

如果以后要给用户用，不能要求他们先装 Go 再跑 `go run`。

建议方向：

1. 后端编译成可执行文件。
例如直接分发 `controller` 和 `node` 可执行文件。

2. 前端打成静态产物。
然后由 Controller 托管，或者由独立静态服务器托管。

3. 提供统一配置文件。
例如把服务器地址、PSK、用户名密码、STUN 列表集中放到配置文件，而不是靠用户手输环境变量。

### 第三层：做真正面向用户的安装体验

如果以后真要落地给普通用户，正确方向不是“把 README 再写长一点”，而是：

1. 安装程序或安装包。
作用：自动放置二进制、初始化配置、注册服务。

2. 常驻系统服务。
作用：Node 开机自动运行，而不是让用户自己开终端执行命令。

3. 图形化配置界面。
作用：让用户填服务器地址、账号密码、节点名称，而不是直接编辑 `.env` 或手敲命令。

4. 自动健康检查。
作用：如果 Controller 地址错了、Relay 不通、TUN 权限缺失，界面要直接告诉用户“哪里坏了”，而不是让用户去看源码日志。

## 十五、现阶段最现实的建议

结合你们现在的项目阶段，最现实的路线不是一步做到“最终用户产品”，而是这样推进：

1. 先把这份手册作为联调标准操作文档固定下来。
2. 先用 `scripts/deploy_server.sh` 把服务器侧的构建、环境模板和 controller + console 托管跑通。
3. 下一步继续补“节点启动、TUN 配置、API 检查”脚本化。
4. 等脚本稳定后，再考虑把前端静态产物和后端启动整成一套演示包。
5. 真要落地给普通用户时，再做安装器、系统服务和图形化配置。

这样推进的原因很简单：

- 你们现在最痛的不是“界面不够花”，而是“联调和演示步骤太依赖开发者记忆”。
- 把启动和验证脚本化，比继续手写更多说明文档更能解决问题。


## 十六、Windows 端支持评估

如果你问“现在要把 Node 的数据面直接落到 Windows 宿主机，麻烦不麻烦”，结论是：麻烦，而且不是简单改几个命令参数就能解决的那种麻烦。

### 1. 哪一部分最难

真正难的不是 Controller，也不是前端，而是 Windows 上的 Node 数据面。

原因：

- Controller 主要是 HTTP + UDP 服务，Go 在 Windows 上运行问题相对小。
- 前端本身就是浏览器页面，Windows 端基本不是难点。
- 难点集中在 Node 的 TUN 生命周期、地址配置、路由下发、权限模型和防火墙处理。

### 2. 当前代码为什么天然偏 Linux / WSL

当前后端实现里，很多地方直接依赖 Linux 机制，例如：

- `internal/node/tun/tun.go` 直接使用 `/dev/net/tun`
- 同文件里直接调用 `syscall.TUNSETIFF`
- `internal/node/runtime/tun_linux.go` 直接依赖 `ip addr` 和 `ip link`
- 多处通过 `/proc/...` 读取系统信息
- 手册里的排障命令也全部是 `ip`、`ping -I`、`tcpdump`

这意味着当前代码并不是“顺手编译一个 Windows 可执行文件就能跑 Node 数据面”的状态。

### 3. 真要支持 Windows Node，需要补哪些东西

至少要补这几层：

1. TUN 驱动适配层。
需要接入 Windows 可用的虚拟网卡方案，例如 wintun，而不是继续依赖 Linux 的 `/dev/net/tun`。

2. 地址与路由配置层。
需要把 `ip addr replace`、`ip link set up/down` 这一套，改成 Windows 的网卡地址、接口状态和路由表配置方案，通常要么调用 PowerShell / `netsh`，要么直接调 Windows IP Helper API。

3. 权限与安装层。
Windows 上通常不只是“sudo 一下”这么简单，还涉及驱动安装、管理员权限、可能的 UAC 提示，以及首次部署流程。

4. 防火墙与端口放行层。
当前 WSL 场景里你们已经会碰到 Windows 防火墙；如果 Node 直接跑在 Windows 宿主机，这部分必须标准化，不然 UDP 打洞和 Relay 回退都可能表现不稳定。

5. 验证与运维层。
现有验证命令大多是 Linux 写法，届时还要补 Windows 对应的排障教程，例如 `Get-NetIPAddress`、`route print`、`netsh advfirewall`、Wireshark 抓包等。

### 4. 工作量应该怎么判断

按你们当前项目状态，更现实的判断是：

- 只让前端在 Windows 浏览器里访问 Dashboard：几乎没有额外成本。
- 只让 Controller 在 Windows 上运行：中低成本，主要是部署和防火墙适配。
- 让 Node 在 Windows 上运行，但先不做 TUN 数据面：中等成本，需要验证 socket、STUN、日志和服务启动行为。
- 让 Node 在 Windows 上完整支持 TUN 数据面并稳定验证 P2P / Relay：高成本，这是一个独立子项目级别的工作。

### 5. 当前最现实的路线

如果你们当前目标还是“课程落地、答辩稳定、局域网联调顺畅”，最现实的路线是：

1. 继续把 Node 数据面稳定在 Linux / WSL。
2. 先把脚本化、联调手册、自动验证补齐。
3. 如果后续真的被要求支持 Windows Node，再单独立项做 wintun 适配，而不是在现有联调阶段顺手硬塞进去。

这样做的原因很直接：

- 你们现在已经有一条可用的 Linux / WSL 路线。
- Windows Node 的难点集中在驱动、权限和路由，不是“多写几个 if 分支”就能消掉的。
- 如果现在强行并线推进，最容易拖慢的是当前已经能落地演示的主线功能。
