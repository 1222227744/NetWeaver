# NetWeaver 互联验证手册

本文用于联调时验证 NetWeaver 是否实现了节点互联，并区分当前链路是 P2P 直连还是 Relay 中继。

## 结论标准

互联验证分三层：

1. 控制面互联：节点能注册、心跳、发现对端。
2. 链路互联：`edges` 接口能返回节点间链路，类型为 `p2p` 或 `relay`。
3. 数据面互联：开启 TUN 后，节点之间能通过 `virtual_ip` 互相 `ping` 通。

最硬的验收标准是第三层：

```text
ping -I nw0 <peer_virtual_ip> 能收到 64 bytes from ...
```

如果 `edges` 显示 `relay`，但 `virtual_ip` 能 ping 通，说明互联成立，当前承载路径是 Relay。

如果 `edges` 显示 `p2p`，且 `virtual_ip` 能 ping 通，说明互联成立，并且当前承载路径是 P2P 直连。

## 当前联调参数

按实际联调环境替换下面的公网 IP：

```text
Dashboard: http://8.134.57.60
Controller: http://8.134.57.60:8080
Relay: 8.134.57.60:9000/udp
Dashboard username: admin
Dashboard password: change-me
Node PSK: netweaver-dev-psk
```

服务器启动 Controller 时必须下发公网 Relay 地址。阿里云联调建议配置：

```text
NETWEAVER_RELAY_ADDR=8.134.57.60
NETWEAVER_RELAY_PORT=9000
```

否则远程节点可能收到默认 Relay 地址 `127.0.0.1:9000`，导致数据面包发到节点本机而不是阿里云 Relay。

节点建议参数：

```text
node-a: machine-id=nw-node-a, hostname=node-a, data-addr=0.0.0.0:9101
node-b: machine-id=nw-node-b, hostname=node-b, data-addr=0.0.0.0:9102
node-c: machine-id=nw-node-c, hostname=node-c, data-addr=0.0.0.0:9103
```

## 一、控制面互联验证

控制面验证用于确认节点能连接 Controller、注册身份、发送心跳并同步 peer。

### 1. 启动节点

以 node-c 为例：

```bash
cd ~/projects/NetWeaver/backend/code
export NETWEAVER_NODE_PSK=netweaver-dev-psk

go run ./cmd/node run \
  -controller http://8.134.57.60:8080 \
  -machine-id nw-node-c \
  -hostname node-c \
  -data-addr 0.0.0.0:9103 \
  -tun=false
```

node-a 和 node-b 分别替换 `machine-id`、`hostname` 和 `data-addr`。

### 2. 观察节点日志

通过标准：

```text
heartbeat ok
peers synced
```

例如：

```text
heartbeat ok: node_id=... peers=1 action=none
peers synced: node-a(10.0.0.2,p2p)
```

### 3. 观察 Dashboard

打开：

```text
http://8.134.57.60
```

通过标准：

```text
总节点数正确
在线节点数正确
节点表格中能看到 node-a/node-b/node-c
每个节点都有 node_id 和 virtual_ip
```

这一层只能证明控制面通了，还不能证明虚拟 IP 数据面通了。

## 二、链路类型验证

链路类型用于判断节点间当前走 P2P 还是 Relay。

### 1. 登录获取 token

```bash
TOKEN=$(curl -s -X POST http://8.134.57.60:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"change-me"}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

echo "$TOKEN"
```

如果输出一长串 token，说明登录成功。

### 2. 查询 edges

```bash
curl -s http://8.134.57.60:8080/api/v1/dashboard/edges \
  -H "Authorization: Bearer $TOKEN"
```

通过标准：

```json
{"code":200,"msg":"success","data":{"edges":[...]}}
```

重点看每条边的 `type`：

```text
type=p2p    表示 P2P 直连成功
type=relay  表示 P2P 尝试失败，已回退到 Relay
```

如果节点日志中出现：

```text
p2p punch failed: ... falling back to relay
```

并且 `edges` 返回：

```json
"type":"relay"
```

说明 Relay 回退功能正常。

### 3. P2P 成功判定

只有当接口或 Dashboard 边标签显示：

```text
P2P
```

或：

```json
"type":"p2p"
```

才能说明 P2P 直连成功。

如果一直是 Relay，不代表互联失败，只代表当前网络环境下 P2P 打洞没有成功。

常见影响因素：

```text
Windows/系统防火墙未放行 UDP
节点在 WSL2 NAT 后
节点开启 VPN
校园网/公司网/手机热点 NAT 较严格
两端都在对称 NAT 后
```

## 三、TUN 数据面互联验证

TUN 验证用于证明节点之间能通过虚拟 IP 通信。这是最关键的互联验收。

### 1. 停止无 TUN 节点

在当前运行 node 的终端中按：

```text
Ctrl + C
```

### 2. 创建 TUN 设备

每台节点电脑执行一次：

```bash
cd ~/projects/NetWeaver/backend/code
sudo $(which go) run ./cmd/node tun -bootstrap -ifname nw0
```

检查：

```bash
ip link show nw0
```

如果能看到 `nw0`，说明 TUN 设备创建成功。

### 3. 用 TUN 模式启动节点

以 node-c 为例：

```bash
cd ~/projects/NetWeaver/backend/code
export NETWEAVER_NODE_PSK=netweaver-dev-psk

go run ./cmd/node run \
  -controller http://8.134.57.60:8080 \
  -machine-id nw-node-c \
  -hostname node-c \
  -data-addr 0.0.0.0:9103 \
  -tun-name nw0
```

node-a/node-b 分别替换对应参数。

### 4. 获取各节点 virtual_ip

从 Dashboard 节点表格或节点日志中记录每台节点的 `virtual_ip`。

示例：

```text
node-a = 10.0.0.2
node-c = 10.0.0.3
```

实际测试时必须使用页面或日志里的真实值。

### 5. 给 nw0 配置本机 virtual_ip

以 node-c 为例，如果 node-c 的 `virtual_ip` 是 `10.0.0.3`：

```bash
sudo ip addr replace 10.0.0.3/16 dev nw0
sudo ip link set nw0 up
ip addr show nw0
```

node-a 也要配置自己的 `virtual_ip`，例如：

```bash
sudo ip addr replace 10.0.0.2/16 dev nw0
sudo ip link set nw0 up
ip addr show nw0
```

### 6. 互 ping

node-c ping node-a：

```bash
ping -I nw0 -c 4 10.0.0.2
```

node-a ping node-c：

```bash
ping -I nw0 -c 4 10.0.0.3
```

通过标准：

```text
64 bytes from 10.0.0.x
```

失败表现：

```text
100% packet loss
Destination Host Unreachable
```

如果 ping 通，说明数据面互联成功。

## 四、两节点验收也可以

三节点更完整，但两节点也可以验证核心能力。

两节点可以完成：

```text
节点注册
心跳
peer 同步
edges
P2P/Relay 判定
TUN virtual_ip ping
离线恢复
身份复用
```

两节点验收结论写法：

```text
node-a 与 node-c 均在线。
edges 接口返回一条链路。
链路类型为 relay/p2p。
开启 TUN 后，node-a 与 node-c 可通过 virtual_ip 互 ping。
```

## 五、推荐截图和日志

建议保留以下证据：

```text
Dashboard 显示节点在线和链路
edges 接口返回 type=p2p 或 type=relay
节点日志中的 heartbeat ok 和 peers synced
如果是 Relay，保留 falling back to relay 日志
TUN 模式下 ip addr show nw0 的输出
ping -I nw0 <peer_virtual_ip> 成功输出
```

## 六、验收结论模板

### Relay 互联成功

```text
节点控制面注册、心跳、peer 同步正常。
Dashboard 显示真实链路。
edges 接口返回 type=relay。
TUN 模式下 virtual_ip 可互 ping。
结论：NetWeaver 已实现节点互联，当前网络环境下链路通过 Relay 承载。
```

### P2P 互联成功

```text
节点控制面注册、心跳、peer 同步正常。
Dashboard 显示真实链路。
edges 接口返回 type=p2p。
TUN 模式下 virtual_ip 可互 ping。
结论：NetWeaver 已实现节点互联，且当前链路为 P2P 直连。
```

### 仅控制面成功

```text
节点控制面注册、心跳、peer 同步正常。
Dashboard 显示节点和链路。
但尚未完成 TUN virtual_ip ping。
结论：目前只能证明控制面和链路发现正常，尚不能证明数据面互联完成。
```
