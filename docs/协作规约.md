# 团队项目协作规范

技术栈：Go + Gin / Vue3 + TypeScript
人数：3 人

## 一、分支管理规范

### 1. 固定分支

- main：最终稳定可运行版本，严禁直接提交
- dev：开发集成分支，所有功能最终合并至此

### 2. 功能分支命名规则

feature/端标识-姓名-功能描述

- 前端：feature/frontend-xxx-xxx
- 后端：feature/backend-xxx-xxx
- 公共文档/配置：feature/docs(config)-xxx-xxx

示例：
feature/frontend-zhangsan-login-page
feature/backend-lisi-user-api
feature/docs-wanggang-readme

### 3. 开发流程

1. 从 dev 拉取最新代码
2. 新建个人功能分支进行开发
3. 开发完成后发起 PR 合并到 dev
4. 至少一名队友审核通过后才可合并
5. 合并后删除已完成的功能分支
6. dev有可运行的快照经协商后可以合并到main

---

## 二、Commit 提交规范（强制统一）

### 格式

yyyy-mm-dd HH:MM | 分类 | 姓名 | 目录 | 完成内容

### 示例

2026-04-13 14:25 | 前端 | 小明 | src/views | 完成登录页面布局
2026-04-13 15:10 | 后端 | 小红 | cmd | 完成项目入口启动文件
2026-04-13 16:30 | 文档 | 小刚 | docs | 补充项目说明文档

### 提交要求

- 每完成一个小功能就提交，不要堆积大量代码一次提交
- 不提交空提交、无意义提交
- 不提交明显无法运行、报错的代码
- 描述完整清晰，不使用模糊词汇

## 四、代码书写规范

### 4.1 前端（Vue3 + TS）

1. 组件文件使用大驼峰命名：HomePage.vue
2. 变量、函数使用小驼峰：userInfo、getList()
3. 单文件代码行数尽量不超过 300 行
4. 函数功能单一，不写过长逻辑
5. 关键逻辑必须添加注释
6. 禁止提交包含 console.log 调试代码
7. 样式使用 scoped 避免全局污染
8. 统一使用 script setup 语法

### 4.2 后端（Go + Gin）

1. 文件名为小写+下划线：user_handler.go
2. 对外暴露函数/结构体首字母大写
3. 内部函数首字母小写
4. 错误必须处理，禁止随意使用 _ 忽略
5. 每个函数添加简要功能注释
6. 路由统一管理，不分散定义
7. 禁止硬编码 IP、密钥、密码等敏感信息
8. 结构清晰，不嵌套过深

### 4.3 通用规范

1. 不提交依赖文件夹：node_modules、vendor
2. 不提交环境配置文件：.env、本地配置
3. 不提交无用文件、空文件、临时文件
4. 代码提交前进行格式化
5. 不随意删除、修改他人代码

## 五、Tag 版本规范

### 什么是 Tag？

Tag 是给项目某个状态打上版本标记，方便以后快速回溯。

### Tag 命名规则

v主版本号.次版本号

示例：
v1.0    初始可运行版本
v1.1    新增登录模块
v1.2    修复已知 Bug
v1.3    完成页面布局
v2.0    项目完整完成版

### 打 Tag 时机

- 项目首次可运行
- 完成一个独立模块
- 修复重要 Bug
- 项目阶段性完成
- 最终提交版本

## 六、代码审查规则（简单版）

发起 PR 后，reviewer 只需要检查三点：

1. 代码是否可以正常运行，无明显报错
2. 是否会破坏现有功能、覆盖他人代码
3. 命名、格式是否符合团队规范

通过则点击 Approve，不通过则评论指出问题，修改后再次提交。

---

## 七、禁止行为（红线规则）

1. 禁止直接向 main 分支提交代码
2. 禁止直接向 dev 分支提交代码
3. 禁止在他人分支上修改代码
4. 禁止提交账号、密码、密钥等敏感信息
5. 禁止提交依赖包、临时文件、垃圾文件
6. 禁止使用无意义、不规范的 commit 信息
7. 禁止强行合并代码

---

## 八、日常协作流程

1. 开始前拉取最新 dev 代码
2. 基于 dev 新建个人功能分支
3. 按规范编写代码并频繁提交
4. 完成后发起 PR 并通知队友审核
5. 审核通过后合并至 dev
6. 每日同步代码，及时解决冲突
7. 阶段性完成后打 Tag 标记版本
